# Send And Public-Sharing Threat Model

Last reviewed: 2026-07-19.

## Status And Scope

This model is the HON-183 pre-implementation security contract. It describes
the Send product line accepted by ADR 0011 and the controls required before
runtime activation. It is not evidence that Send is implemented, deployed, or
safe for real data.

Current behavior remains the ADR 0009 boundary: `/api/sends`, every child route,
and `grant_type=send_access` return explicit `501 unsupported_feature` after any
enabled global ingress quota check, but before route-specific authentication or
Send-specific storage. Config remains `send-enabled: false`.

In scope for the future product line:

- owner-authenticated encrypted text and file lifecycle;
- anonymous capability discovery and credential negotiation;
- short-lived Send-scoped token issuance;
- public metadata and file-download authorization;
- D1 metadata, private R2 encrypted objects, quotas, abuse reports, audit events,
  cleanup, backup residuals, activation, quarantine, and rollback.

Out of scope for the initial stateful slices:

- server-side plaintext inspection, indexing, malware scanning, or content
  recovery;
- organization-owned Sends and organization policy enforcement;
- email OTP until delivery/anti-spam/privacy/replay controls are approved;
- user-visible legal hold;
- a claim that an issued download URL proves recipient download or decryption.

## Security Objectives

1. The Worker never receives plaintext Send content or the raw URL fragment key.
2. D1 and R2 disclosure alone does not reveal a reusable public capability,
   plaintext password, bearer token, or opaque download URL.
3. Unknown, expired, disabled, exhausted, quarantined, and deleted records do not
   become a practical enumeration oracle.
4. Concurrent requests cannot exceed `max_access_count`, reactivate a tombstone,
   or publish an incomplete file.
5. D1/R2 partial failure can leave an inaccessible orphan, but never a publicly
   active row pointing to an unvalidated or wrong-generation object.
6. Owner deletion, quarantine, expiry, and either independent kill gate stop new
   public authorization immediately; physical cleanup is bounded and observable.
7. Application logs, metrics, audit, abuse, and incident artifacts remain useful
   without containing payloads or link secrets; platform request-log exposure is
   minimized and governed explicitly rather than assumed absent.

## Assets

| Asset                                                | Location                      | Required property                                                                  |
| ---------------------------------------------------- | ----------------------------- | ---------------------------------------------------------------------------------- |
| plaintext Send name, notes, text, filename, and file | client memory/filesystem only | never sent to or decrypted by HonoWarden                                           |
| URL fragment key                                     | recipient/owner client        | never transmitted to the Worker, logs, or analytics                                |
| raw access capability                                | owner/public client           | generated by CSPRNG; never persisted or logged                                     |
| encrypted capability envelope                        | D1 `sends`                    | owner-only recovery; AEAD, key-versioned, never plaintext at rest                  |
| capability keyed verifier                            | D1 `sends`                    | indexed lookup; versioned and purpose-separated; useless without server secret     |
| encrypted metadata/text                              | D1                            | opaque ciphertext, owner-scoped for control operations                             |
| encrypted file body                                  | private R2                    | exact generation-specific key; never public at rest                                |
| creator identifier                                   | owner account/public response | disclosed only when owner selects `HideEmail=false`; never logged/cached           |
| password client hash                                 | request memory only           | verified, never persisted or logged                                                |
| password keyed verifier                              | D1                            | constant-time verification under a dedicated derivation label                      |
| Send access token                                    | client session memory         | short-lived, scoped, generation-bound, no refresh token                            |
| opaque download URL                                  | response/client               | random ticket ID, maximum 60-second lifetime; application-redacted bearer secret   |
| quota/report/audit metadata                          | D1/log platform               | pseudonymous, bounded, redacted, retention-controlled                              |
| capability-envelope secret                           | Worker secret store           | independent versioned root; D1 compromise expands it to all encrypted capabilities |
| lookup/password-verifier and token secrets           | Worker secret store           | separate versioned roots, least privilege, rotation and incident ownership         |
| runtime gate and activation epoch                    | Worker configuration          | default off, out-of-band from D1 restore, environment-specific                     |

Ciphertext is still sensitive. Its length, access timing, owner relationship,
and recipient activity can expose metadata even when content remains encrypted.

## Actors

- an owner with a valid account access token;
- an intended recipient holding the full fragment link;
- an unauthenticated scanner without a valid capability;
- an attacker with a leaked capability but not the optional password;
- an attacker with a leaked Send-scoped bearer token;
- a malicious owner attempting storage, request, or report amplification;
- an authenticated user attempting cross-owner Send CRUD;
- an operator or CI actor with repository, D1, R2, log, or secret access;
- a platform or backup operator able to observe encrypted objects and metadata.

## Trust Boundaries

1. **Owner client to Worker.** Account bearer auth is required, but every ID,
   encrypted field, date, size, state, and content type remains untrusted.
2. **Anonymous client to Worker.** Capability, credential hash, Send token,
   headers, route params, and request rate are attacker-controlled.
3. **Browser fragment to API request.** The client must separate `accessId` from
   the URL fragment key. A regression that sends the key crosses the
   zero-knowledge boundary.
4. **Worker to D1.** Queries must use parameters and owner/state predicates;
   capability lookup uses a keyed verifier, not the raw input.
5. **Worker to R2.** Object keys are server-generated and generation-specific.
   D1/R2 have no shared transaction, so activation and deletion ordering matter.
6. **Worker to download client.** Metadata and opaque URL responses cross an
   anonymous cache/log/referrer boundary and require no-store and redaction.
7. **Worker to logs/metrics/audit.** Request context can contain capabilities,
   tokens, password hashes, URLs, ciphertext, filenames, and recipient PII; all
   must be removed before application emission. Platform request logging is a
   separate pre-Worker boundary with an activation policy and residual risk.
8. **Backup to restore.** A backup can contain ciphertext after live deletion.
   D1 control state can also rewind, so an out-of-band gate and rotated epoch
   must precede restore cleanup and runtime activation.

## Entry Points

The owner surface contains list/get, text create, file metadata create, upload,
upload renewal, update, password removal, and delete. The public surface contains
the `send_access` token request, legacy metadata/file authorization routes, V2
bearer metadata/file authorization routes, returned opaque download URLs, and an
abuse report route. Scheduled cleanup and operator quarantine/kill-switch tools
are privileged entry points.

The dedicated route inventory and field contract are in
`docs/protocol/send-wire-contract.md`.

## High-Risk Abuse Paths

### Capability enumeration

An attacker submits random `send_id` values to token and legacy access routes.
The search space is 128 bits and the D1 lookup value is a keyed verifier. Unknown
values use a keyed deterministic decoy response class so retries for one value
remain stable without revealing a database hit. Missing, inaccessible, and bad-
credential timing classes are padded to bounded envelopes. An IP bucket and
capability bucket are checked before expensive work. `429` includes
`Retry-After` but no existence detail.

The system does not claim perfect indistinguishability. A valid unprotected Send
must eventually return a token, while an unknown one cannot. The invariant is
that the entropy and quota cost make blind discovery infeasible and that errors
do not cheaply classify known inaccessible rows.

### Password oracle and CPU amplification

The client sends `password_hash_b64`, not the plaintext password. The Worker
uses a purpose-separated keyed verifier and constant-time comparison, rather
than running an anonymous attacker-controlled slow KDF. Failed credential
attempts consume stricter IP/capability buckets and produce only bounded reason
codes. The client-side KDF and server secret prevent a D1-only offline oracle.

If an attacker has the URL key, D1, and
`HONOWARDEN_SEND_LOOKUP_VERIFIER_SECRET`, they can test candidate passwords.
Lookup-secret compromise response therefore disables Send, rotates that keyring,
and invalidates generations. D1 plus
`HONOWARDEN_SEND_CAPABILITY_ENVELOPE_SECRET` has a larger blast radius: it
recovers active capabilities and requires regenerating their links/verifiers.

### Bearer token replay

A valid token is intentionally reusable for metadata followed by file
authorization. The bearer replay window is bounded by a five-minute expiry and
current generation/state lookup on every use. There is no refresh token. The
token is never accepted for owner APIs and never placed in a URL. Disable,
credential change, delete, quarantine, or either kill gate invalidates subsequent
API use before nominal expiry.

An attacker who steals a token can replay it inside that bounded window. HON-183
does not claim one-time semantics that would break the expected file flow.

### Concurrent maximum-access bypass

Parallel public requests can all observe the same count if code performs a read
then write. Authorization therefore uses one conditional UPDATE whose predicate
includes `access_count < max_access_count`, active state, timestamps, and
generation. Only the request receiving a returned row may deliver text metadata
or issue a file URL. Text access is counted with metadata delivery; file access
is counted when a download URL is issued.

Retries after a successful file authorization may consume another count because
the returned URL is the unit being limited. Clients should reuse an unexpired
URL. A failed URL-signing step after the D1 increment consumes one count and
raises an alert; no compensating decrement is allowed because it races.

### Incomplete or substituted file publication

A malicious or interrupted upload attempts to make a partial object visible,
reuse a file ID, or finish an old generation after owner update/delete. The row
begins `pending_upload`, public lookup accepts only `active`, and R2 keys are
generation-specific. Activation verifies the expected size/object identity and
uses owner/file/generation compare-and-set. A late completion cannot activate a
newer row. Mismatched objects are quarantined for orphan cleanup and never served.

### D1/R2 split-brain deletion

Deletion, expiration cleanup, or quarantine can succeed in one store and fail in
the other. Public revocation is written to D1 first. R2 deletion is idempotent
and retried only for the exact tombstoned generation-specific key. A stale worker
cannot delete a replacement generation. Storage failure is reported, metrics
and alert state remain degraded, and runtime access stays fail closed.

### Cache, referrer, and download URL leakage

Public metadata, errors, tokens, and URL responses set `no-store` and never use a
shared cache. Before activation, `/api/config`, `/config`, all Send `501`/`503`
readiness failures, and public errors have header regression coverage. R2 is
private and R2 is never presigned. An opaque download URL contains only a
32-byte random ticket ID and authorizes one D1-recorded Send/file/access and
object generation for at most 60 seconds. It uses `Content-Disposition` as an
attachment and is removed from application request/audit logging and referrers
generated by a HonoWarden page.

The edge sees a URL before Worker redaction. Platform request logs can therefore
observe the random ticket ID. Activation requires evidence that request-log
exports for the ticket route are disabled or exclude path, query, referrer, and
authorization fields, and that instant-tail/operator access is restricted,
audited, and retained minimally. Platform observation remains a bounded residual
risk; this model does not call the URL "never logged."

The ticket route rechecks current D1 state and kill switch and atomically consumes
a short-lived D1 request/byte budget before opening the R2 stream. This permits
bounded range/retry behavior without unlimited replay. Disable or containment
invalidates an already-issued ticket. Bytes already sent on an in-flight response
cannot be recalled.

### Abuse reporting as an oracle

An attacker can submit arbitrary capabilities to the report endpoint or mass-
report a valid Send. The endpoint validates shape and quotas, stores a
pseudonymous capability reference and fixed reason enum, and always returns the
same generic `202`. It does not reveal existence or auto-delete from one report.
Operator quarantine requires policy thresholds or explicit review and creates a
redacted audit event.

### Retention and backup resurrection

Expired/deleted live data is revoked at the D1 timestamp. Encrypted payload and
R2 object cleanup completes within 24 hours; a payload-free minimal tombstone may
remain for seven days. A backup residual can retain encrypted payloads for the
documented 35-day backup residual. A restore cannot trust D1 feature, kill-switch,
or cleanup-heartbeat state from that snapshot.

The default-off `HONOWARDEN_SEND_RUNTIME_ENABLED` gate and its activation epoch
live out-of-band from D1. Fresh-target restore is preferred. Before an unavoidable
in-place restore, operators set the runtime gate false, read back disabled public
behavior, rotate the activation epoch, and then restore. Cleanup and synthetic
verification run before D1 receives a matching post-restore marker. Tests must
prove that a snapshot containing an enabled feature record and clear D1 kill
switch cannot reactivate a stale public link under a mismatched epoch.

There is no initial legal hold. Adding legal hold without disclosure would break
the deletion promise and requires a separate approved design.

## Failure Matrix

| Failure                                    | Safe request result                                                                     | Required recovery                         |
| ------------------------------------------ | --------------------------------------------------------------------------------------- | ----------------------------------------- |
| D1 unavailable before lookup/mutation      | `503`, no R2 write/read authorization                                                   | error telemetry and availability alert    |
| R2 unavailable during upload               | row remains `pending_upload`; fail request                                              | retry or bounded pending/orphan cleanup   |
| R2 write succeeds, D1 activation fails     | object remains inaccessible                                                             | generation-safe orphan cleanup and alert  |
| D1 tombstone succeeds, R2 delete fails     | link remains revoked                                                                    | idempotent retry; retention alert         |
| quota store unavailable                    | anonymous/owner operation fails closed                                                  | `503`, quota health alert                 |
| audit persistence enabled but unavailable  | operation fails according to audit criticality contract; never silently claims evidence | incident triage and repair                |
| token/verifier secret missing or invalid   | config false; Send routes `503` after source activation                                 | restore versioned secret or roll back     |
| cleanup heartbeat stale                    | config false for activation; kill switch available                                      | repair scheduled job and drain backlog    |
| partially applied migration                | migration marker mismatch; `503`                                                        | forward repair; no destructive guess      |
| restored D1 contains enabled feature state | out-of-band epoch mismatch; config false and public routes fail closed                  | cleanup, new marker, full activation gate |
| platform ticket-log policy is unproven     | activation blocked; no file ticket URLs issued                                          | disable/export-safe fields and read back  |

## Audit Redaction

Allowed event fields are event type, request ID, owner user ID for owner actions,
HMAC-pseudonymous Send/account/IP references, auth method enum, result class,
generation, byte-size bucket, quota class, and timestamps. Public events omit
owner identity when it is not operationally required.

Forbidden fields include raw capability, URL fragment key, access or account
bearer tokens, password/client hash, OTP, recipient email, download URL,
R2 key, encrypted name/notes/text/filename/body, request/response body, and raw IP.
This application redaction happens before console or D1 serialization. It does
not claim to rewrite platform request logs that observe the URL before the
Worker. Field-name deny tests supplement an explicit allowlist.

## Retention And Privacy

- active Send data: until a required deletion date no more than 31 days in the
  future at each accepted create/update;
- abandoned `pending_upload`: no more than 24 hours;
- live tombstone/object cleanup: within 24 hours of deletion eligibility;
- request quota buckets: shortest operational window plus bounded cleanup;
- download ticket budget rows: no more than five minutes;
- abuse reports: 90 days unless an approved incident record requires less/more;
- audit metadata: existing 365-day policy;
- payload-free minimal tombstone: seven days for idempotency/reconciliation;
- backup residual: the existing 35-day backup residual, inaccessible until
  restore cleanup passes;
- legal hold: unsupported in the initial product line.

Recipient email is not stored because email OTP is deferred. When that feature
is reconsidered, normalized-address matching, encryption, anti-spam, delivery
logs, OTP expiry/replay, access/export/delete rights, and retention must be added
to this model before implementation.

## Metrics, Alerts, And Incident Controls

Required metrics are token requests by result class, password failures, quota
rejects by bucket class, text/file access authorizations, bytes authorized,
pending upload age/count, activation CAS failures, orphan count/age, tombstone
backlog, R2 deletion failures, cleanup heartbeat age, abuse report volume,
quarantine count, and kill-switch state. Dimensions use bounded enums and
pseudonymous identifiers only.

Required alerts cover sustained enumeration/credential failures, quota-store
failure, signing/verifier errors, abnormal egress, stale cleanup heartbeat,
old pending/orphan objects, deletion backlog beyond 24 hours, audit persistence
failure, migration marker mismatch, and any active feature with missing control.

Incident containment order:

1. set `HONOWARDEN_SEND_RUNTIME_ENABLED=false` and the D1 kill switch, then read
   back that either independently keeps config disabled;
2. verify token, metadata, new file authorization, and issued ticket access fail
   closed;
3. quarantine targeted Sends or the entire product line;
4. preserve redacted event IDs/metrics, not secret request material;
5. rotate the compromised keyring independently and invalidate access
   generations; for capability-envelope compromise, regenerate every surviving
   capability/verifier and treat all prior links as exposed;
6. repair forward, drain cleanup, rotate the activation epoch, and run synthetic
   lifecycle/rollback evidence;
7. re-enable only through the full activation gate.

## Verification Requirements

Before public activation, tests and live synthetic evidence must cover:

- owner/cross-owner authorization matrices;
- invalid, decoy, expired, disabled, exhausted, quarantined, and deleted access;
- concurrent final-count requests with exactly one success;
- credential bucket and `Retry-After` behavior without existence leakage;
- stale token generation and bearer expiry;
- partial upload, wrong size, late generation, D1 activation failure, and orphan
  cleanup without deleting a replacement object;
- D1-first tombstone with R2 deletion failure/retry;
- cache headers on `/api/config`, `/config`, Send readiness failures, public
  errors, and tickets;
- application log/audit redaction plus platform request-log field/export and
  access-policy readback for ticket paths;
- old enabled snapshot under a mismatched out-of-band activation epoch, followed
  by fresh-target or disabled in-place restore and pre-activation cleanup;
- both kill gates and rollback without touching cipher attachments;
- pinned official client text/file lifecycle using synthetic ciphertext only.

## Residual Risks

- Anyone with the full fragment link can decrypt unprotected content; this is
  the intended capability model.
- A stolen bearer token is replayable inside its short lifetime.
- A random Worker ticket ID is replayable for at most 60 seconds while the Send
  remains active and may be visible to platform request logs; current-state and
  both kill-gate checks invalidate it before a new stream.
- Traffic timing, ciphertext length, storage size, and quota activity remain
  metadata.
- A distributed attacker can consume some Worker/D1/R2 capacity before alerts
  and aggregate controls react.
- Compromise of D1 plus the active capability-envelope secret recovers every
  encrypted live capability under that key and requires link regeneration.
- Compromise of D1 plus the active lookup/password-verifier secret plus a link
  key permits password guessing.
- Backup systems retain encrypted deleted data for the documented residual.
- This design requires independent review and live evidence; document tests do
  not prove implementation correctness.
